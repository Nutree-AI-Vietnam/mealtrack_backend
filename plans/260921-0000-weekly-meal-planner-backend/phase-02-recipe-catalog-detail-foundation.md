# Phase 2: Recipe Catalog Detail Foundation

## Overview

Extend the current curated catalog so the weekly planner can render a full
recipe without introducing a second `recipes` source of truth. Keep nutrition
derived from canonical food references and make seed/import validation strict.

## Requirements

- Add recipe-detail metadata needed by the handoff: source name/URL, prep and
  cook time, tag, allergen disclosure, summary/description, and equipment.
- Add an ordered, immutable `meal_catalog_steps` relation with a stable
  `(catalog_id, step_number)` constraint. Do not reuse `meal_instruction_steps`:
  those rows belong to user-created `meal` records and cannot be the catalog
  recipe authority.
- Add ingredient grocery category (`produce`, `protein`, `pantry`) to the
  catalog ingredient projection; keep `food_reference_id`, display name,
  quantity, and unit as canonical identity/measurement fields.
- Extend the content manifest/importer and content hash to include the new
  detail fields. Existing manifests remain valid with nullable optional detail
  fields, while production import rejects malformed steps/categories.
- Derive macros/calories on read using the existing converter and integrity
  policy. Do not store client-provided macro totals as authority.

## Architecture

Use additive Alembic schema changes generated by
`./scripts/development/migrate.sh generate "add_weekly_recipe_detail_fields"`.
The catalog repository returns one immutable `CatalogMeal` projection with
detail fields and steps. List responses use a compact projection; detail reads
hydrate ingredients and ordered steps. The existing snapshot service may use a
compact form for ranking and must not incur step/detail hydration.

## Implementation Steps

1. Confirm the Phase 1 authority decision, then add only missing catalog
   columns, catalog steps, and category fields; preserve current four-table
   recommendation history and existing `meal_catalog` IDs.
2. Update ORM, domain projection, repository load options, compact/detail
   mapping, seed DTOs, canonical content hash, and strict validator.
3. Generate the migration through the repository CLI, implement a valid
   downgrade, and add schema checks for foreign keys, ordered steps, category
   values, and nullable backward compatibility.
4. Add deterministic fixtures for one complete Vietnamese recipe and one
   legacy-minimal recipe. Verify derived macro/calorie values against the
   backend formula.
5. Keep source URLs and attribution as content fields; never fetch arbitrary
   remote URLs during a user request.

## Tests After / Scenario Matrix

| Scenario | Expected evidence |
|---|---|
| Ordered steps | Stable order, duplicate step numbers rejected |
| Invalid category/unit/quantity | Import fails closed before writes |
| Missing food reference | No published recipe; resolver report is actionable |
| Legacy manifest | Import remains valid with absent optional detail |
| Nutrition mismatch | Stored/returned calories are macro-derived |
| Snapshot read | Ranking loads no steps or source metadata unnecessarily |
| Detail read | Ingredients/steps are catalog data and complete |

## Function / Interface Checklist

- `CatalogMealSeedWrite` and content-hash inputs include every persisted detail
  field.
- `catalog_meal_response` and the future recipe-detail mapper share one
  nutrition projection; no duplicate calorie formula.

## Risk Assessment

Adding recipe fields to the wrong table can create two authorities. Mitigate by
keeping catalog identity/content in `meal_catalog` and using the existing
`food_reference`/conversion path for nutrition; reject a design that makes
user-created `meal` rows the recipe catalog.

## Security Considerations

Treat source URLs and recipe text as untrusted content. Bound field lengths,
step counts, and manifest size. Do not log full manifests or provider data.
